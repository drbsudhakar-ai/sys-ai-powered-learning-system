# P0-013.3 — Common, Individual & Hybrid Learning Session Behavior

**Project:** SYS — AI-Powered Learning System
**Parent Feature:** P0-013 — AI Lecturer & Multi-Mode Learning Sessions
**Previous Tasks:**

* P0-013.1 — Learning Session Domain & Persistence Foundation
* P0-013.2 — Learning Session Management APIs

**Status:** Planned

---

# 1. Objective

Implement the behavioral layer that makes the three P0-013 learning modes function correctly using the shared Learning Session infrastructure:

```text
COMMON
INDIVIDUAL
HYBRID
```

P0-013.1 established the domain and persistence foundation.

P0-013.2 exposes that foundation through HTTP APIs.

P0-013.3 now establishes the **actual behavioral semantics** of each learning mode.

The central architectural requirement is:

> COMMON, INDIVIDUAL, and HYBRID must remain one Learning Session architecture with mode-specific behavior—not three separate learning systems.

# 5. COMMON Session

A COMMON session represents shared learning delivered to multiple authorized participants.

Example:

```text
Teacher / AI Lecturer
        │
        ▼
   Common Session
        │
 ┌──────┼──────┐
 ▼      ▼      ▼
Student Student Student
 A       B       C
```

All participants receive the common session activities unless the session explicitly contains a supported participant-specific activity.

---

# 6. COMMON Session Rules

Implement behavior such that:

1. Multiple authorized students can participate.
2. Session activities can be common to all participants.
3. Common activity ordering is consistent for all participants.
4. Session objectives are shared.
5. Completion can be tracked per participant where required.
6. Evidence can identify the individual participant.
7. One participant's evidence does not overwrite another participant's evidence.
8. One participant's completion state does not incorrectly complete the session for everyone unless the session-level rule explicitly requires it.
9. Facilitator/session-level state remains distinct from individual participation state.

This distinction is important:

```text
Session Status
```

must not be confused with:

```text
Participant Progress
```

---

# 7. Participant Progress

A common session may have:

```text
Session
 ├── Student A → 100%
 ├── Student B → 60%
 └── Student C → 80%
```

Therefore the architecture must support participant-level progress/evidence without creating separate sessions.

Do not automatically assume:

```text
session.completed = every participant.completed
```

unless that is explicitly the existing domain rule.

---

# 8. INDIVIDUAL Session

An INDIVIDUAL session is intended for one student's personalized learning interaction.

Conceptually:

```text
Student
   │
   ▼
Individual Session
   │
   ├── Objective 1
   ├── Activity 1
   ├── Activity 2
   └── Evidence
```

---

# 9. INDIVIDUAL Session Rules

Implement behavior such that:

1. An INDIVIDUAL session has exactly one student participant.
2. A second student cannot be added.
3. The participant must be authorized.
4. Participant-specific activities are allowed.
5. Evidence is associated with the individual student.
6. Session progress is attributable to that student.
7. Another student cannot access the session.
8. Facilitators/admins may access it only according to existing authorization rules.

Do not implement personalization algorithms here.

P0-013.3 establishes the infrastructure for individualized behavior.

Actual intelligent personalization will be expanded by later components.

---

# 10. HYBRID Session

A HYBRID session combines:

```text
Common Learning
+
Individualized Learning
```

Conceptually:

```text
                 HYBRID SESSION
                       │
            ┌──────────┴──────────┐
            │                     │
      Common Activities     Individual Activities
            │                     │
      ┌─────┼─────┐          ┌────┼────┐
      ▼     ▼     ▼          ▼    ▼    ▼
      A     B     C          A    B    C
```

The important characteristic is:

> Students participate in the same session but may receive different activities or learning paths within that session.

---

# 11. HYBRID Session Rules

Implement behavior such that:

1. Multiple students can participate.
2. Common activities can be assigned to all participants.
3. Participant-specific activities can be assigned to individual participants.
4. Common activities remain shared.
5. Participant-specific activities remain isolated to their intended participant.
6. Evidence identifies the participant.
7. Participant progress can differ.
8. Session-level completion remains distinct from participant-level completion.

Example:

```text
Hybrid Session
│
├── Common:
│   ├── Introduction
│   ├── Lecture
│   └── Example
│
├── Student A:
│   └── Practice Activity A
│
├── Student B:
│   └── Practice Activity B
│
└── Student C:
    └── Practice Activity C
```

---

# 12. Activity Scope

Activities must have a clear scope.

At minimum support:

```text
COMMON
PARTICIPANT_SPECIFIC
```

Where:

```text
COMMON
```

means the activity applies to all authorized participants.

And:

```text
PARTICIPANT_SPECIFIC
```

means the activity applies only to its assigned participant.

The exact implementation must reuse the existing P0-013.1 activity model where possible.

Do not create a duplicate activity entity.

---

# 13. Activity Visibility

The API/service layer must determine whether a participant can see an activity.

For a participant:

```text
COMMON activity
        → visible

Their own participant-specific activity
        → visible

Another student's participant-specific activity
        → not visible
```

Facilitator/admin visibility must follow existing authorization rules.

Do not expose another student's individualized activity simply because both students belong to the same hybrid session.

---

# 14. Activity Ordering

Common activities should have a deterministic sequence.

Example:

```text
1. Introduction
2. Lecture
3. Example
4. Discussion
5. Practice
```

Participant-specific activities may be inserted into or follow the common sequence according to the existing activity model.

Do not create separate ordering mechanisms for each mode.

If an activity ordering conflict occurs, return a controlled validation error.

---

# 15. Session State vs Participant State

This is an important architectural distinction.

A session may have:

```text
Session = IN_PROGRESS
```

while:

```text
Student A = ACTIVE
Student B = COMPLETED
Student C = NOT_STARTED
```

Do not represent participant state by modifying the global session state.

If participant-specific progress state does not already exist and is genuinely required, introduce the smallest appropriate persistence extension.

Avoid unnecessary schema changes.

---

# 16. Participant Progress

The implementation should provide a consistent way to determine participant progress based on available:

* activities
* activity completion
* learning evidence
* participant status

Do not introduce a separate progress engine.

If progress calculation is needed, implement it as a focused service/helper consistent with existing SYS architecture.

Do not duplicate P0-012 performance analysis.

---

# 17. Learning Evidence

Learning evidence must remain participant-specific where the evidence originates from an individual participant.

Example:

```text
Common Activity
     │
     ├── Evidence(Student A)
     ├── Evidence(Student B)
     └── Evidence(Student C)
```

Do not allow one student's answer/evidence to overwrite another student's evidence.

For participant-specific activities:

```text
Activity A
   └── Student A evidence only
```

Student B must not be able to submit evidence against Student A's activity.

---

# 18. Session Completion

Distinguish between:

### Session-level completion

The facilitator/session lifecycle reaches:

```text
COMPLETED
```

and:

### Participant-level completion

An individual participant completes their assigned activities.

For example:

```text
Session: COMPLETED

Student A: COMPLETED
Student B: COMPLETED
Student C: INCOMPLETE
```

Whether incomplete participants are allowed when the session is completed must follow the existing domain semantics.

Do not silently invent a new completion policy.

If a policy is missing, implement a conservative rule and document it in tests.

---

# 19. Common Session Creation Rules

For COMMON:

* facilitator must be authorized
* session must have an appropriate academic scope
* multiple students can be added
* participants must belong to the authorized academic context
* common activities are allowed
* participant-specific activities may be supported by the shared infrastructure

---

# 20. Individual Session Creation Rules

For INDIVIDUAL:

* facilitator/requesting user must be authorized
* exactly one student must be associated
* the student must belong to the authorized scope
* adding a second student must fail
* activities must be accessible only to the intended participant

---

# 21. Hybrid Session Creation Rules

For HYBRID:

* facilitator must be authorized
* multiple students may participate
* common activities are allowed
* participant-specific activities are allowed
* participant-specific activities require a valid participant
* activities for nonexistent participants must be rejected

---

# 22. Authorization

Reuse existing SYS authorization.

Do not create mode-specific authorization frameworks.

Authorization must consider:

```text
Role
Academic Scope
Session Ownership
Participation
Participant Ownership
Activity Scope
```

Examples:

### Student

Can:

* access sessions they participate in
* view common activities
* view their own participant-specific activities
* create permitted evidence

Cannot:

* view another student's private activity
* modify session configuration
* assign activities to another student
* add arbitrary participants

### Faculty

Can manage sessions within authorized academic responsibility.

### Admin

Follow existing administrative authorization.

# 23. API Behavior

P0-013.2 already exposes the session APIs.

P0-013.3 should now make those APIs behaviorally mode-aware.

Examples:

```text
POST participant
```

must enforce individual-session participant limits.

```text
POST activity
```

must validate:

* common activity
* participant-specific activity
* participant belongs to session

```text
GET activities
```

must filter participant-specific activities according to the authenticated user.

Do not create redundant endpoints merely because the mode changes.
