# 5. Required API Operations

Implement the minimum useful API surface.

## 5.1 Create Learning Session

Conceptually:

```text
POST /learning-sessions
```

The actual route prefix must follow existing SYS route conventions.

The endpoint should support:

* title
* description where supported
* session mode
* academic context
* facilitator/creator context
* schedule information where supported
* learning objectives where supported

Do not allow the client to arbitrarily assign:

* creator identity
* unauthorized academic scope
* another user's ownership

Derive protected information from the authenticated user and authorization context.

---

# 6. Get Learning Session

Conceptually:

```text
GET /learning-sessions/{session_id}
```

Requirements:

* authenticated access
* academic-scope authorization
* participant authorization
* appropriate facilitator/admin authorization
* return the session using existing response schemas

A student must not be able to retrieve an unrelated student's individual session.

---

# 7. List Learning Sessions

Conceptually:

```text
GET /learning-sessions
```

The endpoint must return only sessions the authenticated user is authorized to see.

Possible filtering parameters may include:

* mode
* status
* course
* subject
* unit
* topic
* participant
* date range

Only implement filters that fit the existing project architecture and are useful at this stage.

Do not build a large reporting/search system.

---

# 8. Update Learning Session

Conceptually:

```text
PATCH /learning-sessions/{session_id}
```

or the repository's established update convention.

Allow only fields that are legitimately mutable.

Do not allow arbitrary changes to:

* creator
* ownership
* unauthorized academic scope
* immutable identifiers

Respect session lifecycle rules.

For example, a completed session should not be freely modified unless the existing domain rules explicitly allow the modification.

```text

POST /learning-sessions/{session_id}/resume
POST /learning-sessions/{session_id}/complete
POST /learning-sessions/{session_id}/cancel
```

However:

**Do not blindly create one endpoint per state.**

First inspect the existing project's API conventions.

If a generic transition endpoint is more consistent with SYS, use it.

The API must call the existing domain/service transition logic.

It must not duplicate state-transition rules inside the route.

Invalid transitions must return the project's standard validation/business error response.

# 14. Authorization

Authorization is a critical requirement.

Reuse the existing:

```text
backend/app/academic_auth.py
```

and existing authentication/authorization mechanisms.

The API must enforce:

### Student

A student can:

* view sessions they are authorized to attend
* view their own participation/evidence where appropriate
* perform student-allowed actions

A student must not:

* manage another student's session
* add arbitrary participants
* modify facilitator-controlled session metadata
* access unrelated academic sessions

### Faculty

Faculty can manage sessions only within their authorized academic responsibility/scope.

### Admin

Admin behavior must follow existing SYS administrative authorization.

### Cross-Scope Access

Must be rejected.

Do not implement authorization using ad-hoc checks based only on IDs.

# 27. API Design Principle

The API layer should follow:

```text
HTTP Request
     ↓
Authentication
     ↓
Authorization
     ↓
Request Schema Validation
     ↓
Learning Session Service
     ↓
Existing Domain Rules
     ↓
Database
     ↓
Response Schema
```

Not:

```text
HTTP Request
     ↓
Route contains business logic
     ↓
Direct database manipulation
```

Keep route handlers thin.
